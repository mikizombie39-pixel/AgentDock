# 漁協の並行の仕事と、3者の流れの画面（2026-11-05）

デイブの指示（2026-11-05）と SAL の回答をもとに決めた設計。漁協の AI が並行していくつかの仕事を進める中に、網谷水産の照会が入り、成立した取引が後の集計にもつながる流れを、実際の処理と記録で見せる。

## 1. 漁協の実処理（集計案）

範囲：仲買への請求額と荷主への支払額を計算し、「集計案」として漁協の DB に保存するまで。請求書の発行・支払の確定・送金は扱わない。語は「仲買への請求」「荷主への支払」を使い、「仕切り伝票」は使わない。

### 表（owner の移行 022・漁協の DB だけに行が入る）

- `settle_rule`：実証用ルール。漁協の手数料 5%（`fee_permille` 50）・手数料の消費税 10%・仲買への請求の消費税 8%・円未満は切り捨て。`valid_from` つき
- `consignor`：架空の荷主（第一岩瀬丸・第三定置網組合・湾奥えび組）
- `lot_consignor`：ロットの番号 → 荷主（せりのロット A-buri_xl-1 と相対のロット S-buri_xl-1 は第一岩瀬丸、S-aji-1 は第三定置網組合、T-shiroebi-1 は湾奥えび組）
- `settle_run`：集計の実行。`kind`（reconcile 照合・invoice 請求・payout 支払）・`cutoff_at`（対象時点）・`started_at`・`finished_at`・`status`（waiting・running・done・mismatch・stopped）・`total_items`・`done_items`・`additional`（追加の集計か）
- `settle_line`：集計の行。`kind`・`source_kind`（auction_result・trade）・`source_id`・`party`（仲買の組織の番号、または荷主の番号）・`gross_yen`・`fee_yen`・`tax_yen`・`amount_yen`・`rule_id`・`run_id`・`at`。`UNIQUE (kind, source_kind, source_id)`＝同じ元の取引を同じ種類で2回数えない
- `settle_check`：照合の行。`run_id`・`who`（市場・漁協・各仲買）・`expected`・`got`・`ok`・`at`

### 対象と計算

- 対象：確定したせりの結果（市場の `auction_result`）と、市場の帳簿に登録した漁協の売りの相対の取引（`trade` の status=registered・seller=iwase）。仮押さえ（`stock_hold`）は入れない
- 仲買への請求：取引額 ＝ 単価 × 数量。請求の消費税 ＝ 取引額 × 8%（切り捨て）。請求額 ＝ 取引額 ＋ 消費税
- 荷主への支払：手数料 ＝ 取引額 × 5%（切り捨て）。手数料の消費税 ＝ 手数料 × 10%（切り捨て）。支払額 ＝ 取引額 − 手数料 − 手数料の消費税
- 照合：市場の記録の照合番号と、漁協・網谷水産・B社・C社が受け取った公開の部分の照合番号を比べる（`results.fingerprint`）。1社ずつ1件。食い違いは `settle_check.ok=0` と run の status=mismatch。請求と支払は、照合が done の時だけ始める

### 進め方（コードの1件ずつの処理）

- `settle.begin(on_date, cutoff_at)`：業務の開始（せりの結果の公開の直後）に、照合の run を作る（請求と支払は waiting）
- `settle.step(now)`：動いている run ごとに1件だけ処理して保存する（並行）。照合が done になれば請求と支払を running にする。初回の run が終わった後、対象時点より後に成立し、集計の行が無い取引があれば、追加の run（`additional=1`）を作る
- 再開：行の一意の制約と、処理済みの行を数え直す作りで、止まった後に `step` を呼べば続きから進み、二重に数えない
- 実演：サーバーの裏の糸が2秒ごとに `step` を呼ぶ。画面に「実証用データを実処理しています。進行を見せるため、処理間隔を2秒に調整しています。」と出す
- 完了の表示：追加集計待ち（対象時点の後に成立し、行の無い取引）が残る間は、全体を完了と出さない

## 2. 漁協の画面（仲間の型・紺）

- 上：漁協の AI の顔（`mate-figure.js` を使い回す）と、記録から作る見出し
- 中：仕事のカードを並べる（せりの結果の照合・仲買への請求の集計・荷主への支払の集計・照会への回答・取引と追加集計）。各カードに、担当（コード／Claude）・状態・件数・結果と記録への入口
- 下：これまでの記録（今の一覧）
- 読むだけ。配色は紺を軸にし、仲買の画面と分ける

## 3. 全体の流れの画面（3列）

- 列：網谷水産（若い担当者と AI）・社長・岩瀬漁協（AI とコード）
- 各列の状態は記録から出す（作業中・判断待ち・待機）。社長に確認を送った段階は「社長の判断待ち」
- 連絡の線は、いま注目する1本だけを強調する（累積させない）
- 動画では、照会を送った時（約2秒）と、社長の確認・差し戻しの受け渡しに差し込む

## 4. 3回目の本物の通しで確かめること

1. 差し戻しの前に始まった起動が、古い判断にもとづく案を出せない
2. 差し戻しの理由を受けた新しい案から、下見・承認・登録へ進む
3. 成立した取引が追加の集計に入る（追加集計待ち → 反映済み）
4. 二重計上がなく、配分・金額・不足が DB の記録と一致する

その1回の記録を撮影と台本の基準にする。AI の待ちは編集で短くし、その区間に「待ち時間を短縮」と出す。全体は 180秒以内（背景 v9 68.81秒は確定）。

## 5. 試験

- 計算：手数料・税・切り捨ての値を、手で計算した正解と照合する
- 二重計上：`step` を何度呼んでも、行の数と合計が変わらない。途中で止めて新しい接続で再開しても同じ
- 対象時点：初回の後に登録した取引が、追加集計待ち → 反映済みになる。待ちが残る間は完了と出ない
- 照合の不一致：受け取った内容を書き換えると mismatch になり、請求と支払が始まらない
- 仮押さえ：押さえ中の数は集計に入らない
- 画面：漁協の画面のカードの件数と状態が、表の行と一致する。全体の流れの画面で、社長に送った段階が「社長の判断待ち」
