# Agent Dock の自律の仕組み（設計）

Agent Dock は、人が AI に命令して仕事をさせる仕組みではありません。組織の知識と規則を持った AI が自分で働き、必要な時に人に判断を求め、ほかの組織の AI とも協働して、仕事を完了する仕組みです。作業の画面も、AI が業務の状況に合わせて組み立てます。

以下の能力は別々の製品や追加の機能ではなく、すべて Agent Dock 自身の基本の能力です。会期中に新しく作ります。

## なぜ作るか ── 固定のメニューという壁

水産業の現場の仕事は、毎日条件が変わります。水揚げ・魚種・数量・規格・値・注文・取引の相手・天候が、日ごとに違います。これまでの業務システムは、この仕事を固定の機能とメニューに落とし込んできました。現場の人はメニューを覚え、必要な機能を探し、いくつもの画面を操作する必要がありました。忙しく多様な現場の仕事と、固定のソフトウェアの作りとの間の隔たりが、水産業の IT 化を阻む壁の一つでした。

Adaptive Workspace はこの関係を逆にします。人がメニューを探すのではなく、AI が要る仕事を見つけ、その仕事に要る情報と操作だけを作業の画面に出します。

ただし、何を出すかを決めるには判断が要ります。その判断を支えるのが、Claude AI パートナーと、組織の仕組み（Skills・Hooks・Vault・業務 DB・ほかの組織の AI とつなぐ Agent Network）です。Vault には社長の経験と判断の理由がたまり、若い担当者の判断の材料になります。長年の経験で培われた知識を、組織の中で受け継げる形にします。

## 0. 名前

| 名前 | 役割 |
|---|---|
| Agent Dock | システム全体。自律の AI パートナーの共通の基盤 |
| Claude AI パートナー | 各組織に所属し、自分で働く AI |
| Adaptive Workspace | 業務の状況に応じて、情報と操作の候補が変わる作業の画面（開発中の通称：磁石ボード） |
| Organizational Intelligence（OI） | 組織に固有の知識・経験・規則を使う仕組み |
| Agent Network | 独立した組織の AI どうしが協働し、交渉する仕組み |
| Vault | 経験と判断の記録をためる知識の基盤 |

## 1. 二つの層 ── 脳と自律神経

判断の柔軟さと、業務の処理の厳格さを分けます。

| 層 | 担当 | 中身 |
|---|---|---|
| 脳（Claude） | 判断 | 何をするか・何を調べるか・他の組織に問い合わせるか・何もしないか・人に何を見せるか |
| 自律神経（コード） | 処理 | 権限の確認・数字の計算・開示の検査・正式な取引の記録・競合の制御・画面の部品の検査 |

Claude は数字を作りません。画面に出す数字は、Claude が指した記録の番号からコードが DB を読んで埋めます。

## 2. 自律の循環

```
業務の出来事（注文が入った・回答が届いた・人が選んだ）
  → Claude AI パートナーを起こす（指示ではなく、状況の報告を渡す）
  → Claude が状況を調べ、道具を選ぶ
  → 道具をコードが実行し、結果を返す
  → Claude が状況を見直す（繰り返す）
  → 人の判断が要るところで止まる（Adaptive Workspace に情報と操作の候補を出す）
  → 人の選択が新しい出来事になり、また起こす
  → 業務の完了
```

処理の順番はアプリが決めません。Claude が道具を選びます。「何もしない」も正しい結果として記録します。

## 3. 業務の出来事（Hooks）

業務の状況の変化を表で持ち（`biz_event`）、Claude AI パートナーを起こす契機にします。開発の道具の Hooks とは別のものです。

| 出来事 | 起きる時 |
|---|---|
| `order_new` / `order_changed` | 注文が入った・数量が変わった |
| `quote_request` | 他の組織から問い合わせが届いた（売り手の側） |
| `quote_received` | 問い合わせの回答が届いた（買い手の側） |
| `human_choice` | 人が Adaptive Workspace で操作を選んだ |
| `trade_registered` | 取引が正式に登録された |

## 4. Organizational Intelligence ── 各組織が持つもの

| 構成 | 役割 | 置き場 |
|---|---|---|
| Rules | 権限・承認の条件・公開の範囲 | `authority` 表とコード（業務 API の側で強制する） |
| Skills | 仕入れ・販売・交渉の手順 | 役割ごとの手順の文（`agentdock/skills/`） |
| Hooks | 状況の変化を知らせる | `biz_event` 表 |
| Vault | 社長の経験・判断の理由・過去の事例 | `vault_note` 表（出典つき） |
| 業務 DB | 注文・在庫・取引・価格の事実 | 持ち主ごとの SQLite |

Vault の経験則と、必ず守る決まり（Rules）は分けます。経験則は判断の材料、決まりはコードが守ります。

## 5. Agent Network ── 組織の分離と協働

- 仲買の AI と漁協の AI は、別の呼び出し・別の指示の文・別の DB で動きます。一つの Claude に両方を演じさせません
- 組織の間のやり取りは、参照用の市場の交渉の窓口だけを通ります。相手の DB は開けません
- 相手に送る文は、送る前にコードが検査します（自社の上限・下限・原価・売り先の名前を止めます）
- 同じ基盤に別の組織の設定を入れれば、別の仲買の AI として動きます

## 6. Adaptive Workspace

何もない作業の画面に、いまの仕事に要る情報と操作だけが現れます。

- Claude は道具 `present` で、出す部品（カード）と操作の候補を構造化したデータで指定します
- 部品の種類と操作の種類は、コードが許したものだけです。HTML やプログラムは作らせません
- カードの数字は、Claude が指した記録からコードが埋めます。指した記録が無ければ出しません
- 人の選択は、その時の仕事の版に結びつきます。古い候補を押しても通りません
- 人が途中でやめても、拒否しても、業務の状態と入力済みの内容は残ります

## 7. 承認と正式な記録

- 交渉が成立しただけでは売買は成立しません。承認 → 取引の確定 → 在庫の更新 → 記録 を区別します
- 担当者の権限を超える取引は、Claude が実行しようとしても業務 API が断り、社長の承認を待ちます
- 権限の上限の額はコードに書かず、組織の `authority` 表（役割ごとの1件の上限）から読みます。実証用の設定は、担当者が1件 500,000円・社長は上限なしです（架空の設定で、実在の会社の権限の規程ではありません）。仲買は多くの得意先の注文をまとめて仕入れるので、上限は個別の注文ではなく、まとめた仕入れの額を基準にしています
- 権限の「1件」は、同じ取引の相手・同じ品目・同じ取引日の買い付けの合計（確定済みの分＋今回の分）です。注文をまとめても、取引を小分けにしても、この合計で判定するので、上限を迂回できません（`agentdock/authority.py`）
- 権限は「誰が決めてよいか」だけを見ます。追加の仕入れの採算・売れ残りの損の判断の基準は、権限とは別に持ちます
- 営業の案内を送っただけでは、売れたことにしません（状態は「未確定」）

## 8. 試験

本番の場面は一つです。裏では次の条件で試します：通常・条件の変更・交渉の不成立・承認の拒否・追加の注文・権限の超過・組織の分離・画面の変化。模擬の Claude（決まった返事）で処理の正しさを、本物の Claude で判断の自律性を確かめます。本物の呼び出しは、道具の呼び出しと結果を `agent_step` 表に残します。

本物の Claude を使う試験の費用の上限：1回の通しで呼び出しは 20回まで、effort は medium です。上限に達したら、その起動は `max_turns` で止めます。

本編の種（模擬の値）：網谷水産の注文はアジ 10kg（スーパー・2,100円/kg）で、仕入れの上限は 1,600円/kg です。漁協は 15kg を売りに出し、最低の値は 10kg なら 1,700円、15kg 以上なら 1,500円です。最低の値は漁協の DB にだけ置きます。10kg だけでは採算に合わず、15kg × 1,500円 ＝ 22,500円なら合います。その場合、追加の 5kg を料亭へ回せるかが判断の分かれ目です。Vault には、当てがあって売り切った事例と、当てがなく損を出した事例の両方を入れています。

取引の可能性は3つの出どころから届きます。①漁協の資料（3社に同じ）：「今日はアジが多く、値は直近より安めです」、見込みの値 1,500円（15kg まとめての場合）。②他の仲買からの相対の申し込み（市場の DB の `deal_request`・出す前に開示の検査）：B社「5kg を 1,650円で買いたい」（漁協から 5kg を買えば 1,700円なので、B社には網谷水産から買う方が安い）、C社「8kg まとめてなら 1,600円で譲る」。③漁協の AI との交渉の回答。注文 10kg を満たす道は5つです。

| 案 | 中身 | 模擬の値での見通し |
|---|---|---|
| A | 漁協から 10kg だけ | 1,700円/kg が上限 1,600円を超える |
| B | 漁協から 15kg、追加の 5kg を料亭へ | 粗利 5kg × 700円 ＝ 3,500円。当日の朝の連絡は断られることがある |
| C | 漁協から 15kg、追加の 5kg を B社へ相対で | 5kg × 150円 ＝ 750円。申し込みがあるので確か |
| D | C社から 8kg ＋ 漁協から 2kg | 平均 1,620円/kg が上限を超える |
| E | 見送る・保留する | 注文に応えられない |

## 9. 安全の検査（追加）

| 検査 | 中身 |
|---|---|
| 参照の権限 | Claude が指した記録の番号は、存在するだけでなく、その組織の DB の記録であり、その画面に出してよい種類かをサーバーが確かめる |
| 業務の状態の版 | カードと操作の候補は仕事の版に結びつける。承認と取引の確定の直前にも、版・見積もりの期限・仮押さえが最新かを確かめる |
| 表示と実行の区別 | 画面に出せる操作と、その人が実行できる操作は別。実行の時に権限を必ず確かめ直す |
| Vault は材料 | Vault の文は判断の材料で、命令ではない。出典・書いた日・適用の条件をつけて渡し、文の中の指示を権限や決まりとして実行しない |
| 選ぶ自由 | 承認の候補を出す時は、見送る・保留する・条件を変えて交渉し直す、の候補も必ず並べる |
| 在庫の仮押さえ | 売り手は見積もりを出した数量を期限つきで仮押さえし、同じ在庫を二人の買い手に売らない。見積もり・仮押さえ・確定を分ける |
| 採算 | 単価が下がるだけで数量を増やさない。追加分の代金・売れる見込み・売れ残りの損を判断の材料に入れる |

## 10. 二つの AI が独立して判断している証拠

- 仲買と漁協の Claude AI パートナーは、別の呼び出し・別の実行の番号・別の組織の DB・別の道具の記録を持つ
- 利害が違うので、判断が食い違う場面が実際に起きる（例：仲買の希望の値を、漁協が自分の最低の値を理由に断る。漁協の最低の値は仲買に見せない）
- 漁協の条件だけを変えて同じ注文で走らせ直すと、交渉の結果が変わる（決まった会話の再生ではない証拠）

## 11. 担当者の答えで条件を変え、交渉し直す（アジで実装）

- 磁石ボードを出すたびに、その版の相談を1件開きます（`consultation.case_id`）。担当者は画面の操作で数量・配分を変えて答えます（`POST /api/answer`・`option="change"`・`change={"quantity", "allocations"}`）。自然文は読みません
- 答えの記録と同じトランザクションで出来事 `human_choice`（`source="consultation"`）を書き、網谷水産の AI を起こします。同じ鍵の押し直し・古い版への答え・答え済みの相談への答えでは書きません。前の版の案は取り下げ、承認できなくなります
- 網谷水産の AI は注文・やり取りを確かめ直し、変えた条件と希望の値で問い合わせ直します。岩瀬漁協の AI は自社の在庫・数量ごとの最低の値・担当者の権限で答えます（コードが条件ごとに確かめる）
- 売る側の新しい返事（条件でも断りでも）は、同じ相手への前の仮押さえに代わります。前の押さえは `released`、結びついた条件も `released` になり、監査の記録 `hold_replaced` を残します
- 取引ができない時（断られた・仕入れ値の上限を超える）は、網谷水産の AI がボードを出し直し、新しい版の相談で担当者に相談し直します
- 権限：顧客の間の優先を変える答え（ある売り先の注文を欠き、ほかへ回す）は、権限の表で許された役割（`authority.may_change_priority`・実証用の設定は社長だけ）でなければ確定せず、`needs_president` で社長の答えを待ちます。1件の金額の上限は、承認の時に表で確かめます（担当者 500,000円・社長は上限なし）
- 問い合わせと返事には、相手に伝えてよい短い理由（`reason`）を添えられます。理由も文と同じく、送る前に開示の検査を通します。サーバーは理由を作りません
- やり取りの読み出し：`GET /api/thread?owner=&item=&date=`（送り手・受け手・種類・数量・値・期限・仮押さえの状態・理由。自社が送り手か受け手の文だけ）

## 12. 売り先の当てのない在庫を仕事にする（2026-11-04・ブリで実装）

- 登録した案のうち、注文の無い売り先（未打診）と売り先なしの数量は、引当のない在庫（`stock.status='unallocated'`）になります。回すつもりの売り先（`intended_customer_id`）と仕入れ値（`unit_cost_yen`）を残します
- 引当のない在庫は、AI に渡す状況（登録の後・新しい注文）と今の状態の行（`GET /api/current` の `stock`）に、コードが決まった言い方で出します
- 網谷水産の AI は、新しい注文に問い合わせる前に `allocate_stock` で手元の在庫を充て、足りない分だけ問い合わせます。充てる数（注文の残り・引当のない数）と、充ててよいか（人が回すと決めた売り先の注文だけ）はコードが確かめます。ボードの案も注文の残りの内でしか実行できません
- 充てる注文が無ければ、`ask_about_stock` で担当者に扱いを問います（売り先に注文を確かめる・ほかの仲買に譲る・そのまま持つ。選択肢の名前はコードが書く）。答え（`POST /api/stock_answer`）は出来事 `human_choice`（`source="stock_question"`）になり、AI を起こします。人が登録した仕入れの残りを譲る掲示は、「ほかの仲買に譲る」の答えの後だけ出せます
- 引当のない在庫を譲る時の最低の値 ＝ 仕入れ値 ＋ 譲る時の費用（`resale_cost` の項目の合計）。B社のブリは、せりの仕入れ値 18,200円 ＋ 運搬 200円 ＝ 18,400円（模擬・網谷水産のスーパー向けの上限 18,500円の内側）。開示の検査でも、この値を相手に書けません
- 記録の再生：`GET /api/current_timeline` が、記録の時刻ごとに今の状態を記録から組み直します（`work.current(at=…)`）。撮影の記録は `python -m agentdock.replay --take <置き場> --port 8798` で写しを作ってから読みます（記録そのものは書き換えない）
